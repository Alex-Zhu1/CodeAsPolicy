# 框架设计

PyRUA-Lean 是一个代码驱动的机器人交互框架：Astra 根据任务、能力说明和现场证据生成程序；
程序组合能力并进行局部判断；框架管理执行、证据、预算和控制权交接。

这组文档将整体框架与各 part 的设计分开，供后续实现和审查使用。
Computer Use 提供交互设计参照；当前设计对象是本仓库的完整 Robot Use 流程，
不以实现 Computer 适配器或新增编程语言为当前交付要求。

## 状态与证据范围

- 梳理日期：2026-10-31 UTC。
- 依据：当前工作区的源码、操作文档和测试内容，包括未提交的新增模块；不等同于已发布版本。
- 初版交付为设计文档与文档导航；2026-11-01（Asia/Singapore）开始落实 P0/L0 首批计时与离线汇总，范围见 [实施记录](roadmap.md#首批实施记录p0l0-计时与离线汇总)。
- 初版依据静态阅读，延迟专题另核对历史日志与官方文档；首批实现以 fake backend 和合成轨迹测试，未新运行模型或机器人性能实验。
- 源码引用以仓库相对路径和符号标识，便于核对当前工作区；不把未提交实现链接到远端已发布代码。

文档使用以下状态措辞：

| 标记 | 含义 |
| --- | --- |
| 现有实现 | 当前工作区存在相应代码；适用模式和后端另行注明，不代表全链路已验证 |
| 部分实现 | 局部机制已有，但缺少端到端的数据关联或统一保证 |
| 待补契约 | 建议明确或实现的协议、校验和交接行为，目前不能作为运行保证 |
| 验收场景 | 后续实现应验证的行为，不表示本次已运行或通过 |

这些是逻辑职责，不要求立即按十个目录重构代码。
例如 `arms.py` 当前同时承担代码工具、反馈和部分恢复职责，模块文档说明的是各项职责应遵守的边界。
交互延迟是跨模块的设计要求：控制器持续工作、模型及时出码、动作及任务正确完成需要分别衡量。
相关计时和受控实验从 P0 开始，不等待最后阶段重构。

## 维护方式

实现改变时，应同时更新对应模块的“现有实现”和“待补契约”，并记录适用后端和验证证据。
新增字段的统一定义放在 [公共契约](architecture.md#shared-contracts)，模块文档补充自己的校验与交接规则。
阶段完成以 [推进路线](roadmap.md) 的验收条件为依据，不能只因类型、文件或接口名称已经存在就标记完成。
