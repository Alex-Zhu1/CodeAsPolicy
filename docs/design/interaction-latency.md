## 问题、范围与结论

用户确认的主要等待是 **Astra 给出下一段可执行代码之前的等待**。
因此，框架除了保证动作和证据正确交接，还要设计模型决策的响应时间：
已有明确规则时程序持续工作，需要新判断时尽快取得有用、完整且可校验的后续代码。
底层控制持续运行不能替代这个交互目标。

当前首先保障 Astra 生成并下发高质量、有用动作。闭环按真实依赖处理复杂情况，
减少不必要的核验和模型往返服务于完整任务；单轮代码更快、动作更少或更早失败都不能单独算提速。

初版依据 2026-10-31 UTC 的源码核对、已有运行日志的只读分析和官方接口文档。
2026-11-01（Asia/Singapore）已接入首批 host 计时、直接 OpenAI 请求计时及离线汇总，
范围见 [路线图实施记录](roadmap.md#首批实施记录p0l0-计时与离线汇总)。
随后已在固定 `insert_key`、Codex/Astra/xhigh 路径实测：两次完整运行、两次采集中断，
计划三次完整样本尚未收齐。完整运行的续轮代码等待中位 26.98 s，cell 执行中位 2.89 s，
调用到达前等待占 host 观测窗口 88.4%；两次任务均失败。
详见 [L0 重复基线报告](l0-insert-key-baseline.md)，其中保留中断、缓存、质量和测量缺口。
L1 候选包括 xhigh→high 单因素对照；这些数据不是延迟改善结果，也未证明纯推理耗时占比。
下文的完整计时/准入契约和优化实验仍是目标设计，不能因新增 trace 就视为已经实现全部保证。

随后[整理桌面试跑](../../runs/organize-table-closed-loop-20261101-051031/REPORT.md)失败且原生动作数为 0：
首段等待 32.19 s、续轮中位 8.05 s，首 cell 执行 75.22 s 主要用于定位。
续轮主要是诊断，不能与正常操作轨迹比较并宣称提速。采集衔接、反馈截断和过度前置核验的修复
已经通过真实 smoke，并完成[整理桌面复跑](../../runs/organize-table-normal-progress-20261101-072852/REPORT.md)：

## Computer Use 提供什么参照

官方 Computer Use 文档对 GPT-6 Astra 推荐代码执行：模型生成脚本，应用执行并返回图像和结果，
会话跨调用保留。这与当前框架的代码驱动方向一致，不能用“Computer Use 不需要生成程序”解释速度差异。
参见 [Computer use 官方说明](https://developers.openai.com/api/docs/guides/tools-computer-use)。

用户观察到的近实时体验是对照目标。当前没有相同模型配置、接入路径、输入规模和任务难度下的配对数据，
不能据此推定官方产品的内部实现、固定响应时间，或认为它使用的就是 Realtime API。
这里的低延迟交互与机器人控制器的硬实时保证分别设计、分别验证。

接口比较还需核对接入路径。当前官方说明要求 Astra 工具调用使用 Responses API；
仓库的直接 `openai` runtime 使用 Chat Completions 兼容协议，可能接入另有转换能力的网关。
应记录实际服务、协议与转换责任，再与官方接口比较；不能仅凭名称把网关、Codex 和官方直连视为同一条路径。
这也是后续官方直连接入需要审查的兼容性契约，尚不能解释已有 Codex 样本的延迟。
参见 [官方模型与接口说明](https://developers.openai.com/api/docs/guides/latest-model#update-api-and-model-parameters)。

## 待补齐的计时与决策契约

### 时间点与主指标

每次新判断建立 `decision_id`，每次请求/重试建立 `attempt_id`，每个工具项保留原始 `tool_call_id`。
关联 session、context revision、代码身份、动作与观测身份。下面都是拟议事件：

首批实现保留独立的 `local_call_id` 和可得的 `provider_call_id`；MCP 不伪造后者。
host 的 `code_validated` 只说明现有检查和全 cell 编译完成，尚不等于下表的 `code_ready`。
`feedback_ready` 记录传输内容准备完毕，不证明模型已收到；各工具阶段与缺失项可离线汇总。

```text
feedback_ready → context_ready → request_started
                                  → first_response_event
                                  → tool_arguments_started → tool_arguments_complete
                                  → code_ready → execution_started
                                               → first_useful_effect → feedback_ready
```

| 时间点 / 指标 | 定义与边界 |
| --- | --- |
| `feedback_ready` | 上轮结果与需要交付的观测已可供 runtime 使用；初轮另记任务/初始观测就绪 |
| `request_started` | runtime 向模型服务提交本次请求；外部客户端无法提供时标为缺失 |
| `first_response_event` | 首个服务事件；若只是心跳或元信息，不能称为 TTFT；首 token 可另记 |
| `tool_arguments_complete` | provider 确认完整、不可再追加的工具项与参数已到达；仅语法前缀完整不算 |
| `code_ready` | 完整调用已通过参数、代码与当前执行准入校验；与动作实际开始分别计时 |
| 主要指标 | `feedback_ready → code_ready`，包括准备上下文、重试及收齐可执行代码所需时间 |
| 定位指标 | `request_started → tool_arguments_complete`；工具项完成到 `code_ready` 的校验时间；后续派发等待 |
| 有用进展指标 | 任务/反馈就绪到首个推进任务的动作，或真正补充决策证据的观测；空 cell、打印状态不算 |
| 闭环指标 | Astra 等待占比、调用次数、工具执行与验证耗时、完整任务时间和成功率 |

各时长优先使用同进程 monotonic 时钟；跨进程/服务记录时钟域和对齐误差，不能直接相减不同域时戳。
没有 provider 计时就不能从客户端间隔进一步推导纯推理或排队耗时。
上面的箭头表示主要因果关系；未来并行流程应记录各项真实时点，不能强行相加重叠区间。

首次代码与后续代码分别报告 p50/p95、样本数、超时率；历史小样本不声称提供稳定 p95。
失败、取消、未产生代码的回复、重试和 compaction 都保留；不能只汇总成功请求。
同时记录实际模型/服务/协议、runtime 版本、生效 reasoning、单次 input/cached/output/reasoning token、
图片数量与尺寸、代码长度、恢复原因和任务结果。不记录认证凭据，不要求保存模型内部思考内容。

### 决策期限、过期结果与交接

为每次判断声明交互目标和 deadline，并纳入 episode 预算；具体秒数应按任务类别和基线设定，
当前没有已验证的近实时承诺。超时不能为继续执行旧代码提供依据。
这里的 deadline 限制本次决策产物最迟获准开始执行的时间；已经开始执行的代码继续遵守代码/动作限额，
不因生成期限到达而回滚或被视为已经停止。每个完整工具项在实际派发前还须重查 decision/attempt 有效性、
deadline、episode 状态、预算和观测依赖；`code_ready` 不是永久执行许可。

| 情形 | 负责方与交接 |
| --- | --- |
| 尚无完整代码，决策 deadline 到期 | 会话/runtime 立即撤销本 attempt 的派发许可，按接口能力请求取消；记录本次未派发，供应端是否已停止另记；重试按新 attempt 计量，保留 episode 预算 |
| 完整代码已收齐或校验通过，但排队期间过期 | runtime 在派发前拒绝，记录零派发及原因；需要继续时建立新的决策与准入记录，旧 attempt 不恢复许可 |
| 迟到代码或被替代请求返回 | runtime 依据 decision/attempt 身份拒绝派发，保留审计；不能因为代码合法就执行 |
| 等待期间现场/证据改变 | 观测与上下文标记版本变化；重新校验依赖，失效则交回 Astra 重新判断 |
| 工具已派发后连接断开 | 执行/恢复按动作身份对账；传输重试不能重复动作，不能将取消生成等同于停止机器人 |
| 新工具项到达但前项暂停/结果未知 | 运行时阻断依赖项，交给恢复流程；流式接收不改变这一规则 |
| 等待模型期间设备需要保持或停止 | 执行控制层按已声明能力处理；模型响应速度不能承担伺服和停止保证 |

## 设计选择与待验证实验

### 1. 按判断难度分配推理投入

在动作和证据质量得到针对性改进后，可在相同 Astra、接入路径和代表性任务上对照当前设置与较低投入，
测完整代码就绪和任务质量。降低 effort 不是本轮抓持证据不足或接近未到位的直接修复。
简单的已知目标续行与新场景理解、失败重规划分别统计；复杂情况保留更高投入的升级路径。
官方 Astra 支持 `low/medium/high/xhigh/max`，不支持 `none`；参见
[Astra 模型说明](https://developers.openai.com/api/docs/models/gpt-6-astra)。
这说明存在可测试的配置空间，不证明降档后质量不变或一定达到某个响应时间。
动态调档还需核对所用 runtime 的支持和缓存语义；本次不修改默认值。

### 2. 减少每次判断的不必要负担

把稳定接口/说明书与当前任务事实分开组织；按需加载 skill，压缩已解决历史，保留未决动作、有效证据、
失败尝试与剩余预算。观测选择由当前决策需要决定，不能为减少输入删去依赖关系所需视角或来源。
先做输入和缓存审计，再做摘要/图像策略对照；已有缓存收益也须纳入测量。

整理桌面回归已显示完整 provenance 挤占反馈、定位数值丢失会增加重复查询。
本轮先修复结果可见性：完整审计留存，模型反馈保护数值、限制、异常和来源引用，压缩重复明细。
本轮完整运行仍发现 cell 24 partial 的关键误差/终点被压缩，已在运行结束后补丁中保护完整 ID、
0.0987 m / 23.5° 误差和 final_xyz，并用离线回放核对；尚未在新整轮中验证该补丁。
这些是功能修复；同步调整采集和提示词后的单次耗时不能用于推断上下文压缩的独立性能收益。

代码只覆盖当前证据支持、直到下一个新判断点的阶段；复用持久 namespace 中已经定义的 helper。
避免每轮重写重复计算，但 helper 必须读取或接收当前证据，不能默用旧位姿/旧图片。
当前样本已经是短 cell，因此这项优化的收益需要实测。

### 3. 已有规则留在程序内，未知交回模型

条件检查、有限重试和数值纠偏可以由程序继续，减少不必要的模型往返。
同时保留必要的证据门控和暂停条件；不固定为“每个原语都问一次模型”，也不强制一次生成整项任务。
长程序可能减少总请求数，却增加首段等待或失去必要的新判断，必须同时比较响应时间、总时间和质量。
当前 pause 模式的自动动作后核验仍运行；按需显式 verify 的提示修改不等于降低自动核验频率。
任何频率变更应另做依赖与任务质量对照。

官方延迟指南把输出量、输入量、请求次数、并行和流式体验作为不同优化方向；
本文将它们拆成可验证实验，不把单个措施当作已证实根因。
参见 [Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)。

### 4. 在完整工具项边界探索流式派发

仅当 provider/runtime 可以确认一个工具项完整结束时，才考虑立即校验和执行该项，
不必等待回复中其他独立内容。保留整个 cell 的编译与执行准入检查；不执行 token 前缀。
记录完整工具项与整条回复完成的时间差，证明实际有可节省区间后再实现。
如果主要等待位于工具参数开始之前，流式展示文字不会消除这段等待。

需补齐重复事件去重、断流处理、取消、迟到项拒绝及前项失败后的依赖阻断。
直接 OpenAI 路径还需先确认目标是官方 Responses 直连还是兼容网关，并设计相应协议；
简单把 `stream: true` 填入现有 JSON transport 不构成流式支持。

### 5. 动作期间预计算候选，作为后续探索

可以研究在当前动作执行期间生成下一步候选，但候选必须绑定 context revision、在途动作与前置条件。
实际回执和新观测到达后才确认是否采用；partial、unknown 或证据失效时作废并重新判断。
不允许两个候选同时操作同一环境。此项依赖动作对账、观测版本和恢复准入，不能先于基础契约实施。

### 实验与验收

| 顺序 | 对照内容 | 同时检查 |
| --- | --- | --- |
| L0 | 固定路径、模型、任务、种子，补齐现有配置基线；首轮/续轮、冷/热缓存分组 | 样本数、失败与重试、完整代码时间、真实生效参数 |
| L1 | 每次只改 reasoning、上下文策略或代码组织中的一个因素 | p50/p95、成功率、返工率、约束违反与总成本 |
| L2 | 明确规则的本地继续与更多模型往返；必要时测试完整工具项派发 | 首次有用进展、总任务时间、漏检/错误继续、重复派发 |
| L3 | 满足基础契约后测试候选预计算 | 实际节省、候选失效率、重算成本、过期候选拒绝 |

配置比较使用相同任务分布和可比预算，并通过重复样本报告波动；不从一次更快的成功直接选默认值。
验收时要能解释“首事件更早但代码没有更早”“单轮更快但调用数变多”“平均更快但失败长尾增加”。
将延迟改善与任务质量一起评估；先记录基线，再确定产品目标与可接受质量变化。
真实正常动作链已有单轮实测；后续继续记录首个有用任务动作、权威成功判定、返工和完整任务时长。
smoke 的原生动作数大于 0 是可执行性的最低证据；空爪动作、状态打印和诊断调用不算整理桌面的任务进展。
另外覆盖：完整项在 deadline 前到达、但校验后已过期时零派发；代码就绪后现场变化使依赖失效时拒绝执行；
已经派发的动作在连接断开后进入对账而不重放。

## 各 part 的责任与推进依赖

| Part | 新增设计责任 |
| --- | --- |
| 任务与会话 | 决策目标/期限、episode 预算、迟到请求失效、等待期间会话状态 |
| Astra 与上下文 | 判断粒度、实际推理配置、历史/图像选择、helper 复用和升级条件 |
| 代码运行时与模型接入 | 请求/工具项时点、完整代码准入、协议适配、断流和重复项处理 |
| 观测与证据 | 等待期间时效变化、当前判断的最小充分证据、缓存来源 |
| 执行与恢复 | 保持/停止职责、动作回执对账、候选失效与依赖阻断 |
| 记录与评估 | 跨层计时、按路径和任务分组、延迟与质量联合对照 |

P0 就启动 L0 计时和接口兼容性核查；L1 的受控实验不必等 P3 模块重构。
P1/P2 贯通观测、动作与恢复后，才推进涉及并行派发或候选复用的改造。
P3 再固化经过验证的上下文/推理策略和回归评价。完整依赖见 [推进路线](roadmap.md)。
