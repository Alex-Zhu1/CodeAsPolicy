# 环境能力与机器人说明书

[设计索引](../index.md) · [整体架构](../architecture.md) · [补齐顺序](../roadmap.md)

## 状态与范围

本文依据 2026-10-31 UTC 当前工作区静态分析，包含未提交的模块和改动。
“现有实现”描述代码当前表达的行为，不代表已完成实机或运行验证。
`CapabilityManifest` 等名称是目标契约草案，尚不是已经实现的公共类型。
本模块负责让 Astra 知道当前环境提供什么能力，以及如何正确使用这些能力。
Computer Use 仅作为接口设计参照；本设计不要求增加 Computer 适配器。

## 职责边界

- 说明机器人身份、机械结构、相机、坐标系、单位、姿态和夹爪语义。
- 列出本次会话实际开放的能力，以及每个能力的副作用、限制和返回保证。
- 使模型看到的说明、生成代码可调用的接口、适配器实际支持的能力保持一致。
- 区分固定设备知识、运行配置、经验性 skill 和本次观测得到的事实。
- 支持简单的 `robo.move_to(...)`、`robo.move_both(...)` 等领域表达。
- 不替 Astra 决定抓取、交接或任务顺序，不定义必须遵守的固定任务工作流。

能力实现可以是驱动、数值规划器或 VLA policy；模型仍通过具体领域 API 组合它们。
说明书声明能力保证；[执行控制](execution-control.md)负责落实并报告实际覆盖。
[观测与感知](observation-perception.md)提供现场事实，说明书不能替代实时观测。

## 输入输出

| 方向 | 内容 | 约定 |
| --- | --- | --- |
| 输入 | `TaskSpec` 中的环境和约束 | 任务授权范围与设备可用能力共同限定调用范围 |
| 输入 | 实际适配器、运行配置、设备描述 | 以当前加载的后端为准，不能只依据机器人类名称 |
| 输入 | API 签名、结果类型、设备知识 | 应能追溯到版本和来源 |
| 输出 | `CapabilityManifest` | 声明能力集合、语义、限制和保证；目前为草案 |
| 输出 | 模型可读说明与 API 参考 | 与本次代码会话实际绑定的 `robo` 对应 |
| 输出 | 能力缺失或契约不一致信息 | 进入 `DecisionContext`，必要时形成 `HandoffReport` |

## 现有实现

- `src/pyrualean/prompt.py` 的 `api_reference` 从实际类签名、docstring 和结果类型生成参考。
- 同文件的 `_public_members` 排除私有成员和 `ABSENT_MEMBERS`，`vla_hidden` 处理不可用的 VLA 能力。
- `src/pyrualean/_robot.py` 的 `effective_primitives` 结合请求配置与 `SUPPORTS_VLA` 决定能力集。
- `RobotBase._refuse_hidden` 在调用端拒绝隐藏能力并记录；因此限制不只是提示词约定。
- `RobotBase` 用 `CAMERAS`、`IMAGE_ARTIFACTS`、`STATEFUL_TOOLS` 等类级信息描述部分设备属性。
- `src/pyrualean/knowledge/` 存放按机器人和配置区分的操作知识。
- `src/pyrualean/arms.py` 的 `arm_contract`、`robot_words` 组装执行方式相关说明。
- `src/pyrualean/coordination.py` 的 `Pose` 明确 world/TCP、米和 `[w,x,y,z]` 单位四元数。
- `CoordinationMixin.motion_capabilities` 可查询同步执行器实际声明的能力覆盖。
- `src/pyrualean/hosts/robodojo_coordination.py` 的 `Controller.capabilities` 明确不提供臂间碰撞、物体碰撞、力控和速度控制保证。

目前已有按运行裁剪的说明书和领域语义；统一、带版本且可验证的 `CapabilityManifest` 尚待建立。
不能把某一适配器的同步、观测或停止保证推广到所有机器人。

## 待补齐契约

`CapabilityManifest` 至少应描述以下内容，字段名称仍待接口设计确认。

| 内容 | 必须回答的问题 |
| --- | --- |
| 身份与版本 | 当前 session 操作哪台设备、哪个适配器、哪版接口？ |
| 能力与可用性 | 方法存在、当前可用、满足前置条件是否是三个不同状态？ |
| 输入约定 | 坐标、单位、姿态、控制点、夹爪命令分别如何解释？ |
| 观测依赖 | 方法依赖哪个 `ObservationSnapshot`，何时判为过期？ |
| 副作用 | 是否运动、是否推进环境时间、是否只操作控制器内部状态？ |
| 返回保证 | 返回表示请求接受、动作结束，还是实际到位？ |
| 检查覆盖 | 检查了哪些几何或控制约束，哪些没有检查？ |
| 资源与中断 | 消耗哪些 `BudgetSnapshot` 项目，取消与停止支持到什么程度？ |

说明材料宜按四层组织，内容可按需加载：

1. 框架核心说明：代码执行、反馈、预算、暂停与后续代码提交。
2. 环境能力说明：本设备的 API、坐标、限制和可用状态。
3. Skill：适用条件、验证办法、故障诊断及可选择的程序模式。
4. 实时反馈：`ObservationSnapshot`、`ActionReceipt`、`EvidenceRecord` 和剩余资源。

Skill 是经验和策略建议，不能扩张适配器能力，也不能把建议写成当前现场已经成立的事实。
文档中的“只读”还应注明读取历史记录或采集当前现场，二者不能混用。
同名方法若在不同适配器中具有不同保证，应明确差异或在绑定时拒绝不兼容用法。

## 失败交接

| 情形 | 本模块的处理 | 接收方 |
| --- | --- | --- |
| 能力不存在或本次被禁用 | 执行前拒绝，给出实际能力集合 | Astra 选择可行策略 |
| 参数、单位或坐标不兼容 | 给出明确参数契约，不猜测或静默变换 | 生成代码修正 |
| 要求的检查不可用 | 明确拒绝该保证，不静默降低检查等级 | Astra 重评约束与方案 |
| 设备、标定或能力版本变化 | 使旧能力上下文和相关目标失效 | 重新观察并构建 `DecisionContext` |
| 文档与后端不一致 | 停止依赖该保证的动作，记录差异 | [恢复交接](recovery-handoff.md) |

拒绝发生在动作前且能够证明没有副作用时，才可以报告“未执行”。
若能力调用已经进入后端，实际效果应由 `ActionReceipt` 和执行系统核实。

## 验收场景

- 同一机器人在 no-VLA 配置下，参考文档与运行调用都不开放 VLA 方法。
- 模型要求臂间碰撞保证时，不支持该检查的后端明确拒绝，而非完成运动后补说明。
- 输入单位、四元数顺序或 TCP/EEF 控制点不符时，在动作前给出具体错误。
- 一个 API 返回“请求接受”时，说明书不把它写成“动作已完成”。
- 历史图像读取和新观测采集在文档、预算和返回元数据中可以区分。
- Skill 中的经验判断不会覆盖新的传感器证据或扩张本次能力集合。
- 改变设备或标定版本后，旧 `DecisionContext` 中的目标需要重新确认。
- 简单顺序操作仍可直接写 `robo` 调用，无需先构造框架工作流对象。
