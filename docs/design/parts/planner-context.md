# Astra 上下文与决策交接

[设计索引](../index.md) · [整体架构](../architecture.md) · [推进路线](../roadmap.md)

## 状态与范围

本文基于 **2026-10-31 UTC 当前工作区的静态梳理**，任务卡与轻量执行计划更新至 **2026-11-02 UTC**，包括尚未提交的模块与修改。
现有实现以 prompt 和工具反馈组织上下文；`DecisionContext`、`HandoffReport` 等统一协议仍是设计草案。
整体面向 Robot Use；Computer Use 只帮助理解“模型生成代码、程序执行、反馈后再判断”的闭环。
本文描述模块责任，不规定抓取、搬运、交接或释放的固定任务状态机。

## 职责与边界

Astra 根据任务、当前现场和能力说明选择目标、动作顺序、双臂角色、验证方式与局部修复策略。
上下文模块负责把这些决策所需的信息明确呈现，避免把历史图像、旧变量或未知结果当成当前事实。
生成 Python 表达任务策略；执行器落实动作；验证组件给出证据，均不代替 Astra 决定完整任务方案。
模型选择代码返回边界：确定规则可以留在程序内，新判断才交回模型。

| 决策层 | 负责什么 | 交回条件 |
| --- | --- | --- |
| 程序内闭环 | 条件分支、有界重试、已知数值纠偏 | 缺少可用分支、局部额度耗尽或证据不确定 |
| Astra 模型闭环 | 解释现场、改变假设、调整策略、判断候选完成 | 新代码、继续观测或有证据的终止声明 |
| 底层执行 | 伺服、同步、执行约束与停止机制 | 动作回执、故障或停止状态；不等待模型维持控制 |

在线 cells 可以形成模型闭环；离线生成、单次 program 和固定 RSI 程序不自动获得这一能力。

## 输入输出

| 方向 | 内容 | 当前载体 / 目标草案 |
| --- | --- | --- |
| 输入 | 权威任务与限制 | `TaskCard` / `TaskSpec` 草案 |
| 输入 | 真实 API、设备坐标和能力限制 | 生成的 API reference、knowledge / `CapabilityManifest` 草案 |
| 输入 | 当前状态、图像及其来源 | 工具反馈 / `ObservationSnapshot` 草案 |
| 输入 | 动作归属、执行状态、证据与预算 | ledger、supervision、recovery / 对应统一协议草案 |
| 输出 | Python 代码、声明的检查、局部纠偏范围 | `python` 或 `run_program` 请求 |
| 输出 | 当前子目标、下一步、完成依据与进度声明 | `plan(...)` / `execution_plan.json`，由 Astra 维护 |
| 输出 | 完成、失败或确认 stuck 的判断 | `finish(status, summary)`，不等于任务权威判定 |

## 现有实现

- `src/pyrualean/play.py`：`build_prompt()` 按执行契约、API、机器人知识、任务卡拼接初始上下文。
- `src/pyrualean/prompt.py`：`api_reference()` 从实际类签名和 docstring 生成接口；`render_prompt()` 生成离线程序提示。
- `src/pyrualean/arms.py`：`arm_contract()` 加入恢复语义和策略 helper 说明；`RECOVERY_NOTE` 要求检查返回值并逐次读取依赖反馈。
- `src/pyrualean/arms.py`：`ArmToolkit._python()` 保存 cell 源码、保留 namespace、捕获暂停和错误，并返回现场反馈。
- `src/pyrualean/arms.py`：`_observe_result()` 附 observation_id、state_version、动作 ledger 范围和图像来源信息。
- `src/pyrualean/openai_runtime.py`：`run_openai_agent()` 处理直接模型循环，失败或暂停后跳过同批后续依赖工具请求。
- `src/pyrualean/play.py`：`play_episode()` 保存实际 prompt 及 hash；外部 Codex、Claude 客户端各自管理对话循环。

正常返回值如 `reached=False` 可以由 Python 自行处理；代码错误和监督暂停要求先读取现场再重规划。
cell 中断不会回滚先前赋值；赋值右侧被中断时，目标变量甚至可能仍保存上一轮值。
统一工具入口现按请求 ID 去重，并在失败后校验反馈版本与恢复标识；MCP 在入队前记录版本，
直接 openai runtime 也保留同一回复内后续调用的跳过逻辑。细节见[恢复与交接](recovery-handoff.md#请求逻辑操作与重启恢复)。

### 任务卡完整记录与精简摘要

保留现有分工：RoboDojo 提供任务和公开观测，PyRUA 确定性整理 `TaskCard`，Astra 根据它规划。
`card.json` 保存原文、未舍入的机械臂初始测量、完整能力快照、字段来源、观测 ID 和时间域、
图片来源及校验值；原生 host 另存观测文件的路径与校验值。没有来源 ID 时保留 unknown。
记录索引 step 0、该次观测的 native steps、建卡时的剩余预算分别记录，避免混为同一时刻。
不会把隐藏物体真值或评测成功标记装入任务卡。

给 Astra 的 prompt 使用精简视图，保留任务原文、初始状态、预算和关键能力边界，
明确图像与状态的对齐情况；完整 JSON 与校验值留在文件中。旧卡仍可加载，LIBERO 呈现保持兼容。
初始卡不会随动作自动更新，当前现场仍从观测与反馈读取。

交互式 cells / program 新增 `plan(goal, next_action=..., done_when=..., evidence=..., status=...)`
和 `plan()`，记录一个当前子目标；每次更新覆盖当前便笺并追加历史版本。
它不是任务分解 DSL，也不新增工具回合或固定动作流程。`done` 只表示 Astra 对该子目标的声明，
不写入任务卡、验证结果或完成判定，不绕过 watch、预算或 finish。
episode 目录中的 `execution_plan.json` 与 `execution_plan.jsonl` 关联卡文件校验值、
已有观测和动作上下文；代码后续报错不撤销已保存的便笺，后续动作也不会替它更新证据。
独立离线生成策略没有这个 helper，其 prompt 不宣称可用。

### 局部对象组规划

2026-11-05 起，在线 `cells` / `program` 的共享 `PLAN_PROMPT` 默认指导 Astra
根据当前观测考虑局部对象组：选择成员、逐成员完成条件、依赖关系、需保持的周边状态与离开条件，
比较共享靠近和局部换位的成本，优先复用合适的作业位置。一个组可以包含多次接触、不同方向或抓取，
不要求一次直线动作或同时接触所有成员；接近并不等于接触几何兼容。

成员身份、待处理 / 已观测完成 / 不确定状态、证据引用与活动操作 ID 记录在现有 `plan()` 文本字段中。
这仍是模型维护的便笺，没有新增可执行批处理 API、自动成员调度器或权威完成状态。
接触后检查实际效果，再决定局部换位、补做未完成成员或离开；依赖失败与新视觉判断仍是返回边界。
中断后先核对活动操作回执，已知剩余路径沿用原 ID 续接，对未知或被带动的成员重新观测，不能重放整组。

RoboDojo 的通用意图知识补充手指接触覆盖、局部退让和双臂路线兼容的检查，
不包含特定任务名称、坐标、对象数或演示动作序列。运动步长、速度、跟踪阈值与预算规则没有随此改动。

## 待补齐的契约

`DecisionContext` 是待实现的统一输入草案，建议至少表达：

| 字段组 | 内容 | 约定 |
| --- | --- | --- |
| 身份与版本 | session_id、task_id、context_revision、能力版本 | 不混用其他会话或设备的事实 |
| 事实与证据 | 观测引用、有效证据、未决问题、已失效目标 | 每个事实保留来源；unknown 不转为 false 或 true |
| 执行现场 | 已执行动作、部分结果、在途与未知动作 | 核对结果后再生成可能重复的副作用 |
| 任务进展 | 已建立关系、当前假设、失败尝试、剩余工作 | 进展必须有证据；假设与任务要求分开 |
| 决策资源 | `BudgetSnapshot`、局部阶段额度、恢复次数 | episode 与跨 cell 阶段额度继续累计；代码调用额度按自己的作用域建立 |

输出仍以普通代码为核心；可以记录其依据的 context revision、预期结果和交回条件，不强制增加任务 DSL。
`HandoffReport` 草案应统一暂停原因、来源、执行位置、当前证据、未完成义务和允许的下一步。
不应要求模型每次重述全部历史；压缩上下文时保留未决动作、有效依赖、失败尝试和预算依据。
阶段名称与事实问题版本需要稳定；更名不能作为绕过未满足依赖的方式。
P0 定义字段和责任，P2 让暂停恢复使用统一报告，P3 再统一各模型 runtime 的上下文消费。

### 出码延迟与判断粒度

本模块与模型接入共同负责“当前反馈到下一段完整代码”的响应目标，详见 [交互延迟设计](../interaction-latency.md)。
现有代表日志中 cell 中位仅 6–10 行，仍有数十秒调用间等待；不要把缩短代码作为未经验证的唯一方案。
记录实际输入/缓存、图像、推理配置和工具参数完成时点，对 reasoning 和上下文策略做单因素对照。
Codex 默认 `xhigh` 与直接 OpenAI 的 `extra_body` 配置属于不同路径，必须记录生效值。

程序覆盖当前证据支持的阶段，在新判断边界返回；复用已有 helper，同时检查其证据是否仍有效。
已知数值规则可本地继续，复杂解释或策略改变再交回 Astra。等待期间现场变化必须反映在 context revision，
过期请求返回的代码不得直接派发；决策 deadline 与剩余额度由会话提供。
这些测量与受控对照从 P0 开始，不等待 P3 上下文重构。

## 失败交接

| 情况 | 处理者 | 下一步 |
| --- | --- | --- |
| 明确可恢复的数值结果 | 当前程序 | 在既定分支与额度内纠偏，验证后再继续 |
| 代码错误或效果已确认的部分执行 | Astra | 阅读 `HandoffReport`，核对现场，只修复剩余工作 |
| 动作结果未知或停止未确认 | 执行系统先接管，随后 Astra | 核对回执和现场；确认恢复范围前不放行依赖动作 |
| 视觉不确定或矛盾 | Astra / 观测与验证 | 选择新的有效证据或独立动作，不盲目重复投票 |
| 相同策略没有进展 | Astra | 改变有证据支持的假设；确认 stuck 后触发配置的恢复 |
| 模型供应端失败 | runtime / 会话管理 | 记录错误与已发生动作，不能自动重放已执行代码 |
| 上下文缺失或过期 | 上下文模块 / Astra | 保留缺口并重新观察，不补造当前状态 |

## 验收场景

1. 同一段代码前半段已移动、后半段报错，下一轮上下文能准确说明已执行与未执行的部分。
2. 暂停中断 `result = move(...)`，模型不会把旧 `result` 当作新动作回执。
3. recoverable 返回允许程序局部纠偏；关键执行故障阻止后续依赖动作并交回模型。
4. 同批模型回复包含代码和提前提交的 finish，代码失败后 finish 被明确跳过或拒绝。
5. 上下文压缩后仍保留未决动作和阶段剩余额度，不自动重试已经失败的同一策略。
6. 任务要求没有强制顺序时，Astra 可以重新分配双臂角色，而不被框架固定工作流限制。
