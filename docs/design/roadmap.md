显式 shadow/pause 仍注入监督提示并同步调用；复查语义修复不等于采样策略或任务净收益已经验收。

工具往返仍约518秒，变慢主要位于客户端观察到的出码等待。**输入正确性修复已验证，任务性能未改善。**
异常自动附图本轮未触发，仍由回归测试覆盖；图像/动作来源和partial/unknown保证保留。

框架需要同时达到三个结果：

- **及时获得下一段有效代码**：明确 Astra 出码前的等待由哪些环节组成，降低等待时保持任务质量。
- **可靠地交接执行与证据**：程序能知道观测来自何时、动作发生了什么，以及失败后由谁接手。
- **支持完整任务闭环**：Astra 选择策略，Python 组合能力并局部纠偏，执行器落实动作，验证器提供证据。

保留简单的 `robo` API、普通 Python 和已有 helper。抓取、交接、搬运等任务策略由模型结合现场生成。
Computer Use 提供设计参照；当前交付围绕 Robot Use，不把新增领域适配器、编程语言或目录重构作为前置工作。

## 推进方式与依赖

框架以 P 阶段验收能力，延迟以 L 实验判断收益。两条线共享记录和质量标准，但不互相替代：
延迟改善不能证明动作回包正确，契约补齐也不能证明模型响应更快。

```text
现在 ── P0：最小契约、配置与计量约定
     │    ├─ P1-O：观测来源与有效性 ─┐
     │    └─ P1-A：动作归属与停止 ───┴─ P2：独立验证与恢复 ── P3：跨路径完善
     └── L0：可比基线 ── L1：配置/上下文对照 ── L2：本地继续/完整工具项派发
                                                  └─ L3：候选预计算（可选）
```

上图是工作顺序，不表示只按整阶段串行放行。P0 的相关字段明确后，P1-O 与 P1-A 即可分别开始；
P2 的实现可先准备，验收时必须具备该闭环实际依赖的观测、动作和预算保证。
L0 与 P0 同时开始，L1 在可比基线形成后即可开展。
L2 的新增执行行为依赖相应 P1/P2 契约，L3 还依赖候选失效与重新准入机制。

每个增量都贯通“输入 → 执行或核验 → 反馈 → 失败交接”，并明确适用路径。
先在一条具体路径验证，再扩展其他路径，不以所有后端同时完成为首个交付条件。

首轮范围建议如下；实施时将实际版本与配置写入验收记录：

- 延迟基线优先使用已有 `Astra / Codex / cells / robodojo_xpl_rgb` 运行作为起点；新实验固定并记录任务、种子、预算和客户端配置。
- 观测与执行分别验证 native host 和 XPolicyLab Bridge；同名 robot 不代表相同传输与控制保证。
- 直接 OpenAI、Claude、program、RSI 按能力矩阵记录覆盖情况，不把单一路径结论推广到所有模式。

## P0：确定最小契约和可比基线

**主责 part：**[任务与会话](parts/task-session.md)、[说明书与能力](parts/capabilities-manual.md)、
[代码运行时](parts/code-runtime.md)、[记录与评估](parts/records-evaluation.md)。

**交付物：**

1. 为首条路径列出任务要求、权威完成判定、模式、能力范围和预算单位。
   预算分开预留、确认消耗与剩余量，注明 episode/cell/动作作用域；区分代码结束、动作完成、任务完成。
2. 将 [公共契约](architecture.md#shared-contracts) 映射到现有字段，明确生产方、校验方、缺失语义与版本。
   首先落实 session/episode、decision/attempt/tool、动作及源观测关联；完整扩展字段随后续增量细化。
3. 用事件序列表达拒绝未派发、正常完成、确定 partial、派发后 unknown、取消未确认停止；
   给出最小 `DecisionContext` / `HandoffReport` 所需现场、未决动作和预算，供后续链路立即消费。
4. 建立实际配置表与 L0 基线：反馈就绪、完整工具参数、代码校验、执行和返回分别记录；
   外部客户端不可得的时间点标明缺失，已有 rollout 间隔标为代理指标。
5. 定义决策 deadline 与请求失效：完整项在实际派发前重查有效性；生成取消、代码中止和设备停止分别记账。

**通过条件：**首条路径可无歧义表达上述成功与故障序列，指出缺失能力；
计时能区分模型等待与工具执行，并保留失败、重试、断流和压缩记录。
`CallRecord.ok` 不提升为目标达成，反馈编号不提升为源帧编号，总 policy 时间不提升为纯模型耗时。

**未通过时：**补齐对应字段或计时点；缺 TTFT 不阻塞可靠的端到端等待对照，
缺动作归属则阻塞依赖它的执行改造。无需等全部公共类型或全部后端矩阵冻结，才开始已具备条件的增量。

## P1-O：贯通观测来源与有效性

**主责 part：**[观测与感知](parts/observation-perception.md)、说明书与能力。
**入口条件：**对应路径的观测身份、时钟域、对齐及缺失语义已明确。

| 增量 | 交付物 | 通过证据 |
| --- | --- | --- |
| 来源贯通 | 从采集端经记录、程序反馈到 Valen 和日志保留同一源引用；区分采集、接收、读取时间 | 同帧重读不变成新采集；旧图不配新位姿/标定；历史读取不覆盖当前现场语义 |
| 有效观测 | 区分历史读取与新采集，说明等待模型时环境是否变化、采集是否推进环境及其预算 | 无动作时能获得所声明的新观测，或明确报告不支持；不以控制步增长代替新帧证据 |
| 感知绑定 | 定位/反投影绑定输入快照、坐标和标定，缓存保留来源及失效条件 | 历史像素不会静默按当前标定解释；旧先验不成为新测量 |

**未通过时：**来源或对齐问题交观测/host 修复，下游保留 unknown；
缺少新采集能力时记录限制，不用微小动作冒充只读刷新。仅依赖已验证来源的后续工作可以继续。

## P1-A：贯通动作回执、未知结果与停止

**主责 part：**[执行与控制](parts/execution-control.md)、代码运行时、[恢复交接](parts/recovery-handoff.md)。
**入口条件：**动作、尝试、episode 和回包身份，以及预算和确定性语义已明确。

| 增量 | 交付物 | 通过证据 |
| --- | --- | --- |
| 因果归属 | 动作身份贯通派发、回包、程序反馈和日志；隔离迟到、重复、跨 episode 数据 | A 超时后的迟到回包不能完成 B；重复或旧回包不能改写当前动作结果 |
| 未知结果限制 | 表达接受/派发/进展、实际效果与确定性；保留查询/观察和未决动作预算 | 派发后超时不自动重放；未对账前阻断依赖动作；已知 partial 保留实际终点与剩余额度 |
| 取消与停止 | 分开请求取消、接受取消、停止确认；声明等待模型和暂停期间控制器的职责 | 取消返回不代表停止；未确认停止时冲突动作被拦截；支持确认的后端提供执行端证据 |

不支持查询或停止确认的后端，须通过“明确无法确认且维持受限状态”的验收，
不能为了完成阶段伪造确认。保留现有双臂同步、partial、能力检查和有限纠偏语义。

**未通过时：**由执行系统保留未决动作和额度，先对账，再交程序或 Astra；
无法对账时按声明的能力转交操作者或终止恢复路径。不能换一个动作 ID 就绕过限制。

## P2：完成独立验证与恢复闭环

**主责 part：**[验证与证据](parts/verification-evidence.md)、恢复交接、代码运行时。
**入口条件：**所选闭环需要的观测来源、动作状态与预算已通过 P1 验收；不必等待无关感知功能完成。

先验收正常动作可推进，再验收存在真实前置依赖时的完整链路：

```text
独立观测 → 核验一个前置条件 → 条件成立才动作
                    └─ unknown / 过期 / 失败 → 暂停并交回
                          → 补足证据 → 新 cell 从实际现场继续
```

**交付物：**

1. 选择一种已有验证器，分开观测获取、核验和监督规则应用；首次动作前即可建立证据，并单独计量成本。
2. 在 `EvidenceLedger` 上贯通源时效、对象/问题版本、依赖与失效，明确验证 callback 的物理只读范围。
3. 将动作和证据汇入 `HandoffReport`，说明已完成、未完成、未知、剩余预算及下一责任方；
   区分“建议重试”与“具备执行许可”。暂停继续不恢复原 Python 栈、不重放已完成动作。
4. 在最小链路通过后扩展视觉、数值、几何和可用传感器核验，让局部 helper 与模型恢复消费相同约定。
5. 将执行结果未知、设备约束与视觉判断不确定分别处理。动作已经完成但视觉 `held` 为 unknown，
   不等于动作是否执行未知。哪些阶段必须建立何种证据，需要依据任务约束和对照结果设计；
   已声明的 `requires` 仍须遵守，不能靠换名、重问或清空事实绕过。

**通过条件：**同帧重读或重问不增加确认次数；unknown、旧证据与核验异常不能放行依赖动作；
只读核验不能隐式驱动机器人；暂停保留实际效果，stuck 恢复不重置 episode 预算。
可从一次暂停定位其代码、动作、观测、证据与恢复决策。没有新增前置依赖的正常动作不强制
重复显式 verify；自动监督按现有模式执行。必须在真实采集链上证明合法证据能够建立，随后动作能够发生。
契约测试通过只是必要条件。将监督策略升级为默认，还需在固定配置的完整任务中证明质量收益，
并报告增加的模型轮次、工具耗时和总耗时；更多核验或更多正确暂停不自动构成任务收益。

**未通过时：**来源问题回 P1-O，动作/停止不确定回 P1-A，门控或恢复交接问题留在 P2。
需要改变视野时，由程序或 Astra 显式选择动作；验证器不越过自身副作用边界。

## 延迟工作：L0–L3 与框架并行推进

主责是 [Astra 与上下文](parts/planner-context.md)、模型接入/代码运行时和记录评估。
指标与时间点沿用 [交互延迟设计](interaction-latency.md)，不在路线中另造一套口径。
主要比较反馈就绪到完整代码可执行的等待，首次与后续分别报告；同时记录任务质量和总耗时。

| 工作 | 启动条件与交付物 | 通过条件 / 未通过下一步 |
| --- | --- | --- |
| **L0 基线** | 与 P0 同时启动；先统一历史日志口径，再补当前路径计时、配置、样本和缺失字段表 | 能分开工具执行与等待，保留错误长尾；分不清就补对应计时，不先做根因结论 |
| **L1 配置与上下文对照** | 可比基线具备即可开始；在同一路径分别测试推理投入、历史/图像选择、代码组织，每次只变一个因素 | 等待改善且满足事先写明的质量标准；质量退化保留原配置或缩小适用场景，不明确则补同条件样本 |
| **L2 本地继续** | 使用 P1/P2 已验证的观测、预算和暂停约定；比较明确规则在程序内执行与反复交回模型，复用已有 helper | 模型往返或总等待减少，必要验证及交接仍生效；错误继续则修复前置条件和退出规则 |
| **L2 完整工具项派发** | 先证明工具项完成至整条回复完成之间有可节省区间；再验证协议、去重、deadline、迟到拒绝和失败阻断 | 完整代码更早就绪/执行且无重复副作用；若主要等待在工具项开始前，则暂缓此项，回 L1 或请求链路诊断 |
| **L3 候选预计算（可选）** | 对应 P1/P2 契约已通过，且存在可重叠的执行窗口；候选绑定现场版本、动作预期与准入条件 | 节省等待足以抵消失效重算，旧候选不会执行；收益不足则不采用，不阻塞框架交付 |

此前 L0 完整样本的调用到达前等待占观测窗口 88.4%，续轮代码等待中位 26.98 s，
cell 执行中位 2.89 s；因此 `xhigh → high` 仍是 L1 候选，另一候选为上下文/反馈选择。
前次整理桌面控制样本比原版更快但仍低分；输入清理后的最新样本得分仍50、总耗时27.43分钟，
工具往返为原版的1.70倍、反馈文本从4.22倍降为2.31倍，累计出码等待却由616.95秒升至999.67秒。
这两次单样本不能证明反馈精简能稳定提速。键盘与雕像仍未放准，应先复盘动作质量，再对照哪些反馈真正帮助策略，
避免以此前较重配置为唯一基准继续叠加机制。新样本 host 排队、准备、校验、序列化各自中位为毫秒量级。
抓取/接近误差和 held 的可观测性仍需分析，但不能预设“增加核验”就是修复方向。
此前两轮 insert_key 也均失败，不足以证明降档质量可接受，没有证明 effort 是等待根因。
完整工具项派发仍需编译整个 cell，不执行 token 前缀；模型生成取消也不等于已派发动作停止。

每项对照在实验前写明任务/种子/预算、实际配置、重复采样计划、关注的延迟指标和可接受质量变化，
并记录成功率、返工、约束遵守、调用次数和成本。首次/后续、runtime、缓存状态分组；
报告样本数、超时率和分布，小样本不声称提供稳定 p95。
具体交互目标根据 L0 基线和任务需求设定，不预先承诺未经验证的近实时秒数。
只有收益和质量均有证据，才将候选配置升级为默认。

**入口条件：**首条 P1/P2 闭环通过，相关契约和日志足以支持跨路径比较。

| --- | --- |
| 上下文消费 | 将前期已使用的最小 `DecisionContext` 统一到其他目标 runtime；压缩后仍保留任务、有效证据、未决动作、失败尝试和预算 |
| 知识管理 | skill 有适用能力、触发和内容版本，打包核心与参考材料一致；知识建议不冒充实时事实 |
