## 已实施的修复与证据范围

- 运行默认 `monitor-mode=off`，普通程序由 Astra 自查，保留观测来源、动作身份、partial/unknown 和控制器约束。显式 `shadow` / `pause` 仍可启用。
- 启用监督后 `critical=None` 表示空列表；普通问题的 unknown 只提供信息。显式 critical 在连续未知达到上限时触发一次复查，随后新 cell 可以继续，原事实、概率与来源仍保持 unknown。
- 告警与完成候选也只对同一持续条件通知一次。新的已知反证会重新启用通知；unknown、重读同图、换 cell 或换阶段名称不会制造反证。问题版本改变按新问题处理。
- 复查后的接续直接使用 Astra 的下一段已记录程序，不新增审批 API，不伪造 Valen yes。模型根据反馈与现场选择继续、补证据或改策略。
- `requires` / `defer_fact` 保留为显式硬性视觉依赖；新 cell 和普通复查不清除它们。提示词不再要求普通搬运默认登记 held=yes。
- 显式启用 pause 仍要求每 cell 声明 watch，也仍在动作端点同步调用 Valen；采样频率和多来源硬依赖尚未改造。修复默认介入和复查交接，不等于已证明启用监督的任务净收益。

实现集中在 `supervision.py`，同步监督/恢复知识、技能和使用文档。回归覆盖持续 unknown 后接续、
已知证据后再次触发、同源重复、问题版本变更、显式依赖与未决动作保护。
下文的 94 次调用及收益结论仍针对修复前冻结运行，不能作为新版本任务结果。

本批全量回归 **715 passed（127.06 s）**；之后补充的问题版本变更测试 **3 passed**。
相关 Python 文件 Ruff 与差异检查通过；记录见[修复验证](../../runs/valen-handoff-fix-20261101/validation.json)。
这些是代码契约验证；后续任务复跑的证据范围另列如下。

## 修复后的完整任务复跑

[本轮报告](../../runs/organize-table-handoff-rerun-20261101-093121/REPORT.md)采用与原版对齐的 high / on-demand / pure、calls100 / 5400 s，默认 Valen off，专用 stuck 恢复关闭。结果是 **score=50（原版75）**、**20.55分钟（原版27.27）**，首次加 Python 续轮出码等待 **616.95秒（原版1205.31）**。

没有 Valen 调用或视觉门控；99 次高层动作中 94 次产生原生步，8 个 known partial 保留实际结果。其中 7 次运动 partial 后继续了任务，末次 home 在 1000 原生步预算耗尽处截断，随后报告失败。鼠标和闹钟在终图中有明确搬运进展，键盘仍错位、雕像侧躺支架旁、抽屉未开；原生只有聚合分数，不能反推逐物体评分。

这支持默认关闭后的连续执行路径可用，但**没有恢复原版任务质量，也没有在线验证启用 Valen 后的新通知接续语义**。与前一轮同时改变了多项配置，不能把等待收益全部归因于 Valen 修复。后续优先分析这些实际失败中的证据需求，再评价按需触发能否减少返工；不恢复普遍 held=yes 搬运许可。

## 结论

Valen 有潜在价值的角色是：对明确、可观察的局部关系提供额外线索，在有用的决策边界触发 Astra 复查。
目前没有证据证明它适合作为正常搬运阶段的默认、唯一视觉许可来源。

修复前实现把三个职责连在一起：视觉事实回答、复查触发、持续动作准入。
尤其是在复查之后，Astra 没有把其他合法证据用于解除同一依赖的正式渠道，仍需要 Valen 给出所要求的答案。
这超出了“异常时把控制权交回 Astra”的分工。

本次任务证明监督规则会运行、会暂停；没有证明这些暂停避免了真实错误或提高了任务完成质量。
应先评估它相对于 Astra 自查及数值检查提供的增量价值，再决定哪些规则值得成为强制条件。

## 修复前是谁在作出什么决定

| 环节 | 实际责任方与实现 | 影响 |
| --- | --- | --- |
| 定义问题与依赖 | Astra 生成 `watch(facts, critical, alerts, requires, ...)`；注入知识举例 `requires={"held": "yes"}` | 这是模型在框架指导下声明的条件，不能解释为 Valen 自行理解了整个任务 |
| 回答视觉问题 | Valen 收到当前/局部前帧与原子问题，返回 yes/no/unknown 概率 | 不生成动作，也不接收完整任务策略或目标容差 |
| 解码 | 宿主按默认 0.8 阈值将低置信回答归为 unknown | unknown 既可能是模型选了 unknown，也可能是 yes/no 未过阈值 |
| 触发复查 | 告警、关键事实连续 unknown、完成候选、监控异常或预算触发 | pause 模式展开 cell，剩余动作不执行 |
| 阻止后续动作 | `requires` 不满足，以及仍标为 critical 的事实达到 unknown 上限 | 跨 cell 保留；默认 `critical=None` 表示全部问题 |
| 解除视觉依赖 | 现有事实账本由 Valen 观测路径写入，`evidence()` 只返回副本 | Astra 自查图像、夹爪宽度和随动证据，没有通用的有据裁决入口 |

实现依据：[`supervision.py`](../../src/pyrualean/supervision.py) 的 `watch`、`before_action`、
`_evaluate`、`monitor_prompt`；[`evidence.py`](../../src/pyrualean/evidence.py) 的 `blockers`；
[`监督知识`](../../src/pyrualean/knowledge/astra_valen_supervision.md)。

启用后的 Valen 在动作原语结束后同步调用，不检查 `move_to` 内部的连续轨迹，不能承担伺服层的即时停止职责。
`shadow` 也同步调用、产生反馈并注入监督知识，只是不执行相同的暂停行为；它不是零成本、零策略影响的旁路。

## 能否判断“拿取”和“放到指定位置”

不能简单划为“拿取可以、放置不可以”。现有接口能问任意已声明的局部视觉关系，
[契约示例](../../skills/astra-valen-supervision/references/contracts.md)也包含物体在托盘内、竖直、抽屉齐平等问题。
但能提出问题不等于已有可靠性保证。

| 判断 | Valen 可提供的证据 | 还需要什么 |
| --- | --- | --- |
| 物体是否位于夹爪之间 | 可见物体/夹指关系，前后帧中的局部变化 | 隐藏接触、稳定抓持不能仅由外观保证；需要结合随动、夹爪状态与任务情境 |
| 闹钟是否在柜顶 | 身份、柜顶和物体关系清楚时，可提供视觉判断 | 明确目标表面；遮挡时需其他视角或允许的测量 |
| 是否放在“指定位置” | 若指定位置具有明确可见标记，可判断粗略关系 | 目标定义、允许误差、姿态要求；精确容差通常需要几何测量 |
| 整理任务是否完成 | 按需回答部分最终事实 | Astra 整合全部目标；基准测试保留原生评测的最终裁决 |

当前请求没有独立的任务目标图、目标坐标/容差或完整计划上下文；如问题只说“指定位置”，
Valen 不会自动知道指定在哪里。抓持同样存在可见外观与真实支撑之间的差距。
`holding=True` 也只是夹指未闭合到一起的测量线索，不能被提升为目标物体可靠抓持的保证。

## 建议分工与交接

| 部分 | 应负责 | 不应默认承担 |
| --- | --- | --- |
| Astra | 根据任务、图像、数值状态和动作结果决定阶段、动作、补证据及恢复 | 为了让单个验证器给 yes 而无限改视角、重复核验 |
| Python | 执行阶段内已有规则、有限重试和数值纠偏，必要时交回 | 把未知当作成功，或重放结果未知的动作 |
| Valen | 按需提供局部视觉线索，发现值得复查的变化 | 每个正常动作的唯一批准方、精确几何裁判、整任务裁判 |
| 宿主/控制器 | 身份归属、未决动作对账、预算、设备约束与停止 | 把普通视觉不确定普遍等同于执行状态未知 |

正常路径是“程序执行一个有意义的阶段 → 返回必要图像与结果 → Astra 判断下一步”。
Valen 可以在阶段内提供有价值的提前复查触发，也可以由 Astra 在特定问题上按需调用。
如果它每次都带来额外核验和往返，却没有提前发现问题或减少 Astra 工作，就没有证明其净收益。

普通复查触发后的路径：

1. Valen 报告问题、来源、判断与不确定性；宿主按已选择的复查规则交回 Astra。
2. Astra 综合其他允许的证据，选择继续、补充观测、局部纠偏、改策略或停止。
3. 若允许继续，应记录此次判断的依据与适用范围；保持原 Valen unknown 记录，不伪造为 yes。
4. 真正的未决动作、控制器约束与用户规定的必要条件仍由各自契约处理；Astra 复查不能一并清除它们。

普通复查已用下一段程序承接判断；显式硬依赖的替代证据渠道仍待设计，不能通过改事实名、清空账本或降低阈值来模拟。
普通视觉 unknown 可以作为信息不足随正常反馈返回；是否立即打断，应取决于具体后续动作的证据需求。
对同一来源或同一未改善的可观测性，不应反复触发同一复查。经过验证且有必要的视觉规则，才逐项考虑强制门控。

## 与 Computer Use 的关系

OpenAI 官方的公开 Computer Use 流程允许模型生成代码组合动作，并在一组动作后接收截图检查结果；
公开集成流程没有要求额外的视觉模型逐步批准任务动作。执行环境仍承担权限、取消、预算和结果核对。
这是对公开接口的描述，不能据此断言服务内部没有检查器。
参见 [Computer use 官方文档](https://developers.openai.com/api/docs/guides/tools-computer-use)。

对本仓库有用的参照是保留 Astra 的现场判断与策略主责。机器人额外需要独立持续工作的运动约束与停止机制，
它们的职责也不能交给动作结束后才调用的 Valen。

## 下一步怎样验证价值

1. **先评估问题是否可观察。** 使用[已有离线评估](../guide/valen-evaluation.md)与保存图像，为抓持、掉落、目标区域和遮挡分别建立独立标签；同时覆盖真实异常和正常状态。保存不确定标签，避免只挑清楚的样本。
2. **分别衡量判断与触发。** 除 false-yes/false-no、unknown 和耗时，还需看触发是否对应真实且有后果的问题、是否比 Astra 正常观察更早、是否导致有用的调整。没有触发的片段也要审查，否则无法估计漏检。
3. **比较完整流程。** 固定任务、种子、预算和其他配置，比较 Astra 正常自查与 Valen 辅助复查；重复运行，报告原生得分/成功、总耗时、返工和模型轮次。简单 off/shadow/pause 是配置级对照，提示与反馈也会联动，不能直接归因于某个内部判断器。
4. **按证据选择介入范围。** 先证明某类局部触发有收益，再决定采样频率和是否升级为硬条件。降低 unknown 率、增加暂停次数或通过更多契约测试，都不能单独作为有效性的证据。新版本已允许普通复查后由 Astra 新 cell 接续；这不等于已经证明模型使用了更好的判断或任务收益。

当前可下的结论是：抓持许可的默认强制角色缺乏实测支持；作为可选视觉助手和复查触发器的价值，值得用上述方式验证。
