# 已有实验提炼的开发经验

整理日期：2026-11-04（Asia/Singapore）。下面是开发方法的证据，
不把过去测试数或任务成绩当作当前工作区的验收。原始目录名保持原样。
链接中的 runs 是本地归档，通常不随 Git 分发；文件不可用时不能声称重新核实。

## L01：冻结实际运行源码，才能解释验证结果

- **症状**：测试期间还有其他源码编辑；只记录 commit 不足以定位实际版本。
- **有效做法**：归档 dirty 状态和新增文件，冻结运行源码、记录每文件 hash；
  将“快照未变”和“当前工作区仍等于快照”作为不同检查。最终改动后补相关测试。
- **证据**：[仓库审查](../../../docs/design/repository-review-20261102.md) 的首轮
  777 项通过后，任务卡增量的另一次检查为 84 通过、3 失败，并记录后续源码漂移。
  [后续实验 manifest](../../../runs/hold-reacquire-20261104-1422/manifest.json)
  保存 frozen 文件 hash 和完整配置。
- **范围**：适用于未提交/并行修改；hash 一致只证明清单内文件相同，不证明环境相同或任务成功。

## L02：先区分环境故障与代码故障，再做定向重试

- **症状**：本机 socket 相关测试失败，但并非断言揭示产品行为错误。
- **有效做法**：读取具体异常，确认权限/环境问题；在允许所需本机端口的环境重跑失败项。
- **证据**：[验证清单](../../../runs/repository-review-20261102/verification.json)
  记录 773 项通过、4 项 socket 失败，随后 4 项定向复测通过。
- **范围**：仅限已定位的环境原因。该次后续任务卡 3 项断言失败是另一个问题，不能一并归因于沙箱。
  所需权限仍按当前环境处理；这条经验不意味着关闭沙箱或跳过失败测试。

## L03：完整任务发现问题，固定指令验证具体修复

- **症状**：抓取阶段提前报 `phase_target_not_reached`，不同任务回合步数又不相同。
- **有效做法**：提取同一公开抓取指令，比较阶段判定与最终判定使用的目标；
  修复后用固定指令验证，再看完整任务能否完成。
- **证据**：[跟踪修复报告](../../../runs/shared-tracking-final-20261103-0552/REPORT.txt)：
  原候选在第 26 步提前返回，修复后一次修正完成夹紧和试提，共 46 步；
  最终完整 `general_pickup` 为 100 分/70 步。该批三个代表任务都成功。
- **范围**：证明特定到位判定修复。26→46 是完成性变化，不能称为提速；
  在线策略路径不同，完整回合的步数差异不能单独归因于控制器。

## L04：原生结果与模型声明并列，冲突按原生验收解释

- **症状**：Astra 自报完成，图像接近目标，原生评分仍为零。
- **有效做法**：同时读取 `result.json.environment_success`、`finish` 和
  `bench/eval_result/**/_result.json`；保留冲突，列出已知与缺失的判据证据。
- **证据**：[意图接口报告](../../../runs/intent-policy-final-20261103-1151/REPORT.txt)
  中最终 `push_T` 自报成功，但原生 0 分、591 步、success=false。
- **范围**：模型 finish、动作 completed、原生 success 三者分开。
  原生日志没有各判据误差时，不能仅凭最终图像断言哪一项失败。

## L05：用独立回放定位隐藏在时间序列里的判定条件

- **症状**：木琴动作看似逐键完成，得分却为零。
- **有效做法**：在独立 benchmark 副本增加只读判定日志，原动作回放；
  同时核对动作边界状态，判断诊断能否解释原回合。
- **证据**：[诊断结果](../../../runs/xylophone-verdict-diagnostic-20261103/diagnosis.json)：
  495 原生步；第 172 步首次命中后一直等待抬升。
  [回放报告](../../../runs/xylophone-verdict-diagnostic-20261103/REPORT.txt) 记录 29 个动作边界状态
  与原运行最大差异 0.0；抬升参考是首次命中时的 mallet 高度，不能用最低 TCP 高度代替。
- **范围**：是成功定位失败原因，不是木琴任务成功。该副本没有修改评分规则或生产执行器；
  事后诊断不能混入本轮策略输入或作为允许读取隐藏状态的通用先例。

## L06：自然续接、账本一致与故障注入分别记录

- **症状**：超时后不清楚已执行多少，或者把干净账本当作恢复能力的完整证明。
- **有效做法**：先检查 partial 的 `effect_known` / `execution_complete`，reconcile 后从实际
  状态续接；核对动作身份和预算，避免重播已经执行的准备动作。
- **证据**：[跟踪修复报告](../../../runs/shared-tracking-final-20261103-0552/REPORT.txt)
  的 `push_T` 自然超时发生在已执行 9 步后，对账并换新操作继续，最终 100 分/487 步。
  [意图接口报告](../../../runs/intent-policy-final-20261103-1151/REPORT.txt)
  另有真实模拟器定向取消、续接、重复完成 ID 零动作检查。
- **范围**：均不能证明跨进程丢失状态或掉包恢复；这些结论需要对应故障注入。

## L07：把机制验证与任务收益分开，防止“测试绿了”变成虚假进展

- **症状**：新夹持证据接口测试通过，但插钥匙分数不变。
- **有效做法**：对齐原生步骤和观测，统计实际触发分支及证据维度，再判断新机制是否被用到。
- **证据**：[夹持重关联报告](../../../runs/hold-reacquire-20261104-1422/REPORT.txt)：
  较广回归 215 项、最终相关 76 项通过；完整实验仍为 15/100、997/1000 步、success=false。
  13 次夹持判断中 12 次 unknown、1 次二维 image_consistent，没有三维 following；
  未观察到遮挡后自动恢复完整证据的成功片段。
- **范围**：证明软件分支测试和有限二维证据使用，不证明任务性能改善或三维抓稳。

## L08：保留中断与配置变化，才能做诚实比较

- **有效做法**：保留中断 attempt 的原因和停止时实际动作数；重跑用新目录。
  用户要求扩大原生预算时，用独立副本记录精确改动，与标准预算结果分开。
- **证据**：[中断记录](../../../runs/staged-grasp-20261103-1546/initial-attempt.json)
  保留停止过程中已执行的 19 步，没有把它作为完整评测；
  [预算变更](../../../runs/hold-reacquire-20261104-1422/budget-override.json)
  明确记录 insert_key 的 300→1000 步。
- **范围**：中断记录与完整 episode 的统计口径要明确；不能删除低分轮次或将扩大预算结果与标准成绩混算。

## 更新格式

对已有条目优先补证据或缩小范围。新增条目使用：

```text
ID / 标题：
状态：待验证 | 已验证（注明层级） | 被替代
触发症状与假设：
有效操作 / 最小复现命令：
版本与配置：源码指纹、运行入口、任务/seed、相关预算
证据：测试输出或原始产物路径，实际结果与样本数
适用范围与反例：哪些结论尚不能推广
下一次复用：先检查什么，何时需要重新验证
```

只把经过验证且会改变下次开发决策的做法提升到 SKILL 主流程。
不要将一次任务的坐标、模型选择、机器路径或重试次数提升成所有任务的规则。
